Work / Team analytics agent

A team-facing analytics agent, in daily use by managers.

The problem

Testing information for a product team lives in several places: trackers kept by different groups, and BI datasets with their own definitions. A leadership question such as "where are we on this program?" meant someone pulling from several of them and reconciling the differences. Smaller requests (a status email, a reply to a thread) came in constantly and were mostly the same few patterns.

A wrong answer here is not cosmetic. It feeds decisions about what to test and what to make. So the bar was not "answers quickly". It was "answers correctly, says where it got the answer, and says when it can't".

What I built

The agent has a small set of jobs: answer status and results questions in a structured format, answer higher-level questions that need several sources combined, and draft routine messages for the user to review. It reads data through tools and writes nothing on its own.

Design decisions

One tool per dataset, identifiers fixed

I first thought of one generic "query a dataset" tool. I rejected it: it asks the model to reproduce a long dataset identifier on every call, and one wrong character fails silently as a "not found". Picking among clearly named tools is something a model does reliably. Only the query text is left for the model to write.

Exact values live in the instructions, not the knowledge base

Retrieval is probabilistic: the agent decides whether to search, and what comes back can be truncated or paraphrased. Instructions are read in full every turn. So anything that must be followed exactly (identifiers, the specific workaround for a known tool bug) is in the instructions. The knowledge base is for large reference material where an approximate answer is fine.

Route by the kind of question

People ask this agent about things that are not testing at all: benefits, forms, who to ask. A metrics dataset answers those confidently and wrongly. The instructions say which source answers which kind of question, and that a mixed question runs the sources in parallel.

It drafts. People send.

For anything that would reach another person, the agent shows its planned action and waits. That one rule removes a whole class of failure and made it easier for managers to trust the rest.

The error I caught, and what it taught me

Synthetic example of a real failure

I wrote a rule for available stock as "available minus reserved", from how it was described to me. The live agent then read the data model's own glossary and pointed out that the field is already net of reserved and non-sellable units. My rule would have subtracted reserved stock twice and under-reported what could be sold.

Two lessons. First, a calculation written from a verbal description is unverified until it is checked against the source's definition. Second, and more uncomfortable: I found this because the agent happened to read the glossary, not because anything I had built was designed to catch it. I had no automated evaluation at that point.

That gap is why I built an evaluation harness. The failure is now a case in it (md1), and it is one of ten lessons I wrote up in the playbook.

Rollout

I used it on my own work first, then gave it to managers on the team, who use it. I also confirmed the audience before writing the instructions for a shared version, after getting the scope wrong twice by inferring it from a label instead of asking who would use it and for what. It has not been shared beyond those first users yet.

What this page doesn't show

Honest limits
  • No usage numbers or accuracy figures. I don't have telemetry I can publish, so I won't invent any.
  • The original rollout had no automated evaluation. The harness came after, from the failures above.
  • The data, tools and systems are internal, so you cannot run this. The method is open source in the playbook, and the examples there are synthetic.

What's next

Move this agent onto the evaluation harness and the weekly monitoring report from agent-playbook: a fixed case set built from real incidents, a regression gate before every instruction change, and a log that ties a bad week to the version that caused it.
